# VitaLens ABDM & FHIR R4 Integration Architecture

> [!CAUTION]
> **INTEGRATION STATUS & COMPLIANCE DISCLAIMER**:
> This integration layer implements the **HL7 FHIR R4 data mapping specification** and the **architectural scaffolding for the Ayushman Bharat Digital Mission (ABDM)**. The ABDM client (`ABHAIntegrationClient`) operates **strictly in offline simulation / mock mode**. No real HTTP calls to the National Health Authority (NHA) gateway (`dev.abdm.gov.in` or `abdm.gov.in`) are made. Real ABDM integration requires official NHA sandbox registration, a Health Facility Registry (HFR) ID, Healthcare Professionals Registry (HPR) IDs, and NHA HIP/HIU certification.

## 1. Domain Boundary Isolation & Clean Architecture

A core architectural tenet of VitaLens is that **third-party interoperability specifications do not leak into core domain models**.

```
┌────────────────────────────────────────────────────────┐
│                   VitaLens Core Domain                 │
│  - User (models/user.py)                               │
│  - MedicalReport (models/report.py)                    │
│  - Biomarker (models/biomarker.py)                     │
│  - ReportAnalysis (models/report_analysis.py)          │
└───────────────────────────┬────────────────────────────┘
                            │ (Zero FHIR leakage)
                            ▼
┌────────────────────────────────────────────────────────┐
│         Boundary Adapter: app/integrations/abdm/       │
│                                                        │
│   fhir_mapper.py ────────► Maps relational models to   │
│                            HL7 FHIR R4 Bundle,         │
│                            DiagnosticReport &          │
│                            Observation resources       │
│                                                        │
│   abha_client.py ────────► ABDM Gateway Client Stub    │
│                            (Simulates M1/M2/M3 APIs)   │
└────────────────────────────────────────────────────────┘
```

- **Relational Domain Models**: `MedicalReport` and `Biomarker` store domain-specific fields (`test_name`, `canonical_name`, `value_numeric`, `unit`, `flag`).
- **Translation at Boundary**: Translation to HL7 FHIR R4 JSON schemas occurs exclusively inside `app/integrations/abdm/fhir_mapper.py`.

## 2. HL7 FHIR R4 Resource Mapping Specification

All outputs generated by `map_report_to_fhir_bundle` strictly conform to the HL7 FHIR Release 4 (v4.0.1) specification:

### 2.1 FHIR Bundle (`Bundle`)
- **`resourceType`**: `"Bundle"`
- **`type`**: `"collection"`
- **`timestamp`**: ISO-8601 UTC timestamp
- **`entry`**: Array of packaged FHIR resources (first entry is the `DiagnosticReport`, followed by individual `Observation` resources).

### 2.2 Diagnostic Report (`DiagnosticReport`)
- **`resourceType`**: `"DiagnosticReport"`
- **`status`**: `"final"`
- **`category`**: Standard HL7 v2-0074 category `[{"system": "http://terminology.hl7.org/CodeSystem/v2-0074", "code": "LAB", "display": "Laboratory"}]`
- **`code`**: LOINC coding `11502-2` ("Laboratory Report")
- **`subject`**: FHIR reference `Patient/{user_id}` with patient display name.
- **`effectiveDateTime`**: ISO-8601 report date.
- **`result`**: References to all member Observation resources (`[{"reference": "Observation/obs-xxx", "display": "..."}]`).
- **`conclusion`**: Plain-English AI analysis summary.

### 2.3 Biomarker Observation (`Observation`)
- **`resourceType`**: `"Observation"`
- **`status`**: `"final"`
- **`category`**: `[{"system": "http://terminology.hl7.org/CodeSystem/observation-category", "code": "laboratory", "display": "Laboratory"}]`
- **`code`**: Standard LOINC coding with resolved code (e.g. `1558-6`, `718-7`, `2093-3`) and test text.
- **`valueQuantity`**: Standard UCUM quantity `{"value": float, "unit": str, "system": "http://unitsofmeasure.org", "code": str}`.
- **`referenceRange`**: Array containing low and high reference threshold quantities.
- **`interpretation`**: Standard HL7 v3-ObservationInterpretation codes (`"N"` for Normal, `"H"` for High, `"L"` for Low, `"AA"` for Critical Abnormal).

### 2.4 Canonical LOINC Code Registry (`fhir_mapper.py`)

**Resolution Protocol**:
1. Checks for direct `loinc_code` attribute if set.
2. Exact case-insensitive match on canonical biomarker name in `CANONICAL_LOINC_MAP`.
3. Exact match on raw test name in `CANONICAL_LOINC_MAP`.
4. Substring / alias match (e.g. `sgpt`, `fbs`, `pcv`).
5. Fallback to `"unknown"` only for completely unrecognized custom biomarkers.

## 3. ABDM Milestone Architecture (M1, M2, M3)

The National Health Authority (NHA) mandates a three-tier milestone structure for ABDM compliance:

| Milestone | Focus Area | Real ABDM Specification | VitaLens Current State |
|---|---|---|---|
| **M1** | **ABHA Identity** | ABHA ID creation (Aadhaar/Mobile OTP), verification, and patient registration linkage. | **Simulated**: Format validation (14 digits) & profile storage (`users.abha_number`). Gateway calls stubbed. |
| **M2** | **Health Information Provider (HIP)** | Registering as an HIP, discovering patient records, and linking care contexts. | **Architecture Ready**: FHIR R4 `DiagnosticReport` bundles mapped and ready for care context linking. |
| **M3** | **Health Information User (HIU)** | Patient Consent Manager integration, encrypted data exchange (AES-256 + ECDH key exchange). | **Documented Architecture**: Consent tables aligned with DPDP/ABDM; encryption bridge scaffolded. |

## 4. Production Integration Requirements & Gaps

Plugging in real ABDM production/sandbox infrastructure requires the following steps:

1. **NHA Sandbox Registration**:
   - Register at `https://sandbox.abdm.gov.in` to obtain official `client_id` and `client_secret`.
   - Implement OAuth 2.0 session token exchange (`POST /v0.5/sessions`).
2. **Facility & Professional Registration**:
   - Obtain Health Facility Registry (HFR) Facility ID for clinical entities.
   - Link Healthcare Professional Registry (HPR) IDs for consulting doctors.
3. **Gateway Callbacks & Bridge**:
   - Configure public HTTPS webhook endpoints with NHA gateway signature verification to receive asynchronous ABDM callbacks (`/v0.5/users/auth/on-init`, `/v0.5/links/link/on-confirm`, etc.).
4. **HIU Encryption Bridge**:
   - Implement Elliptic Curve Diffie-Hellman (ECDH) key exchange and AES-GCM data encryption/decryption for data exchange with ABDM Consent Managers.
5. **Certification & Safe-to-Host Audit**:
   - Pass all test cases in the NHA Sandbox portal for M1, M2, and M3.
   - Complete third-party CERT-In empanelled Safe-to-Host security audit.
